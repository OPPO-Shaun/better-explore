### 1.1 核心定位

本调研旨在回答：当我们有大量存量大型项目、涉及多人协作（产品、设计、技术方案、代码架构），且需要让 AI Agent 便捷读取这些知识时，应采用「跟随代码仓库」「开独立仓库」还是「打造专门托管平台」来组织知识沉淀。

### 1.2 组织方式简图

```
┌─────────────────────────────────────────────────────────┐
│                     知识组织三种模式                       │
├─────────────────────────┬─────────────────┬─────────────┤
│   模式一：仓库内置          │  模式二：独立知识仓库 │ 模式三：托管平台 │
│   /docs /adr             │  proposals/rfcs  │ Wiki/       │
│   ARCHITECTURE.md        │  enhancements    │ Confluence/ │
│   AGENTS.md（就近）       │  （跨仓库共享）    │ Notion      │
├─────────────────────────┴─────────────────┴─────────────┤
│         Agent 消费层：需要「机器可读 + 版本受控 + 可低成本拉取」│
└─────────────────────────────────────────────────────────┘
```

## 4. 调研发现

### 4.1 三种模式的典型案例

| 模式 | 代表项目 | 说明 |
|------|----------|------|
| 仓库内置文档 | 中小型项目通用做法 | `/docs`、`/adr`、`ARCHITECTURE.md`、`CONTRIBUTING.md` 与代码同仓库、同 PR 评审、同生命周期 |
| 独立知识/提案仓库 | `kubernetes/enhancements`（KEP）、`rust-lang/rfcs`（RFC） | 承载跨组件、跨版本的设计决策与讨论历史，与具体实现仓库解耦但仍在同一组织下 |
| 专门托管平台 | 企业内部 Wiki / Confluence / Notion | 排版协作体验最好，但对 Agent 最不友好，需要额外的爬取/同步/权限打通管道 |

### 4.2 各模式优劣势

**模式一：仓库内置文档**
- 优势：文档与代码强绑定，改代码时顺手改文档，版本一致性好，Agent "仓库即上下文"读取最直接。
- 劣势：权限粒度粗（产品/设计文档难以与代码分开授权）、非工程角色贡献门槛高、仓库越大 clone/索引越重、历史陈旧文档难清理。

**模式二：独立提案/知识仓库**
- 优势：适合"一对多"场景（一个知识仓库服务多个代码仓库）、审阅流程可独立于代码 PR、非工程角色贡献门槛低、权限可与代码仓库分离管理。
- 劣势：容易与代码"漂移"（改了代码忘更新文档仓库），需要额外的交叉链接（issue/PR 互引）机制让 Agent 能找到对应代码。

**模式三：专门托管平台**
- 优势：排版和协作体验最好，适合面向非技术人员的沉淀（产品、设计文档天然更适合这种载体）。
- 劣势：对 Agent 最不友好——非 git 原生、难以 diff/追溯版本，需要额外集成（API/爬虫/embedding 同步），维护成本高，内容与代码演进容易脱节。

### 4.3 面向 Agent 消费场景的关键考量

- Agent 消费知识的核心诉求是：**可被低成本、结构化地拉取，且与代码版本对齐**。Git 原生仓库（无论同仓库还是独立仓库）天然满足"clone 即可读、纯文本、可 diff、可被 grep/embedding 索引"的要求；Wiki/Confluence/Notion 类平台通常需要额外打通，对 Agent 不友好。
- 业界新兴约定（`AGENTS.md`/`CLAUDE.md`/`llms.txt`）进一步印证：知识应"就近存放、机器可读、版本受控"——即在代码仓库根目录放置面向 Agent 的入口文件，再分层链接到更详细的知识（可在本仓库，也可链接到独立知识仓库）。

## 5. 落地评估

### 5.1 推荐方案：分层混合模式

采用**分层混合方案**，而非单一模式，按知识类型分流：

1. **代码强绑定的技术知识 → 留在代码仓库内**
   内容：架构说明（ARCHITECTURE.md）、模块设计、ADR、README、接口文档、目录级 AGENTS.md。
   理由：改动频率与代码同步，由同一批工程师维护，PR 内联评审最自然，也最符合 Agent"就近读取代码即读到设计"的诉求。

2. **跨项目/长周期的产品与技术方案沉淀 → 独立知识仓库（按业务线/组织粒度，而非按代码仓库粒度）**
   内容：PRD、跨系统技术方案、RFC/提案、评审记录、产品/设计角色产出的沉淀。
   组织形式：参考 KEP/RFC 模式，按目录分类（如 `/proposals/<年份>-<主题>.md`），用状态标签（draft/accepted/superseded）管理生命周期。
   关键：各代码仓库入口文档需与该知识仓库对应条目建立双向链接，避免"孤岛"与"信息漂移"。

3. **不建议单独打造重型托管平台**
   除非已有强烈跨部门协作和检索诉求，且团队有能力维护同步管道，否则优先级最低。若确有非结构化协作场景（设计稿评审、头脑风暴），可作为过程沉淀的临时载体，但最终结论必须回流为 markdown 到 git 仓库，作为唯一事实来源（single source of truth）供 Agent 消费。

4. **面向 Agent 的统一入口层**
   每个代码仓库根目录放置轻量 `AGENTS.md`/`ARCHITECTURE.md`，概述项目结构、关键设计取舍，并链接到独立知识仓库中的详细方案；独立知识仓库用统一元数据（front-matter：项目名、模块、状态、关联仓库/PR/issue）便于检索或建立 RAG 索引；可引入轻量 CI 检查，确保重大代码变更 PR 附带知识仓库文档更新链接，减少漂移。

### 5.2 风险

- 独立知识仓库与代码仓库间的双向链接依赖人工纪律，若无 CI 校验易失效。
- 分层标准（哪些内容归代码仓库、哪些归知识仓库）需要团队共识，否则会出现归类混乱。

### 5.3 接入成本估算

| 阶段 | 工作内容 | 预估工时 |
|------|----------|----------|
| 现状盘点 | 梳理各存量项目现有文档分布（仓库内/Wiki/Confluence/口口相传） | 视项目数量而定 |
| 分层标准制定 | 明确代码仓库 vs 知识仓库的内容归类规范 | 1~2 人日 |
| 知识仓库骨架搭建 | 采用 RFC/ADR 式目录与元数据规范 | 1~2 人日 |
| 存量仓库补齐入口文档 | 为各代码仓库补充 ARCHITECTURE.md/AGENTS.md 并回填链接 | 按仓库数量线性增长 |
| 双向关联机制 | PR 描述引用知识仓库链接、知识仓库引用代码仓库/模块路径 | 视工具链集成程度而定 |

## 6. 结论与建议

> **结论**：
> - ✅ 推荐采用「分层混合模式」：代码强绑定知识留在代码仓库内（就近 Agent 可读），跨项目产品/技术方案沉淀在独立知识仓库（按业务线粒度、参考 RFC/KEP 组织），不单独建设重型托管平台。

### 建议

1. 优先为每个存量代码仓库补齐轻量级 `AGENTS.md`/`ARCHITECTURE.md` 入口文档，作为 Agent 首先读取的索引。
2. 建设一个按业务线组织的独立知识仓库，采用目录分类 + 状态标签 + front-matter 元数据管理产品/设计/跨系统方案沉淀。
3. 建立代码仓库与知识仓库之间的双向链接约定，并视条件引入 CI 校验，降低信息漂移风险。
4. 待检索规模增长后，再评估是否需要在知识仓库之上叠加检索/embedding 服务，而非另起一个重型托管平台。
