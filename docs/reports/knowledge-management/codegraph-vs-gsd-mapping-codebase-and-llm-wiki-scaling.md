### 1.1 核心定位

三者都在解决"让 Agent/人类理解一个大型代码仓库"这个问题，但选择了三条不同路径：**CodeGraph** 用静态分析构建可查询的结构化图谱（图数据库/索引），**GSD mapping-codebase** 用多个 LLM 子代理并行阅读代码后产出结构化 Markdown 摘要文档，**llm-wiki** 类工具用 LLM 遍历/摘要代码后生成互相链接的百科式 Wiki 页面。前两者是本次调研的对比核心，后者是本次重点分析"为什么在文件量变大后会失效"的对象。

### 1.2 三者关系简图

```
┌───────────────────────────────────────────────────────────────────┐
│                     大型代码仓库"可理解化"的三条路径                    │
├───────────────────┬───────────────────────┬─────────────────────┤
│   CodeGraph        │  GSD mapping-codebase  │   llm-wiki 类工具     │
│   静态解析 → 图谱     │  LLM 子代理 → 摘要文档     │  LLM 遍历 → Wiki 页面   │
│   (Tree-sitter/LSP) │  (Read/Bash/Glob/Grep) │  (chunk + summarize) │
├───────────────────┴───────────────────────┴─────────────────────┤
│              产出物形态：图数据库/索引 vs 结构化 Markdown vs 互链网页文档 │
├───────────────────────────────────────────────────────────────────┤
│         规模扩展性：CodeGraph 近线性 > GSD 分治可控 > llm-wiki 明显退化   │
└───────────────────────────────────────────────────────────────────┘
```

## 2. CodeGraph 调研：作用与优势

### 2.1 是什么

CodeGraph 是一类"代码知识图谱"工具的统称（代表实现如 `codegraph-ai/CodeGraph`、`colbymchenry/codegraph`），核心做法是：用 Tree-sitter（或语言原生 LSP）对代码仓库做**静态解析**，抽取函数、类、模块、导入、调用链、继承关系、依赖关系等结构化实体与边，构建成一个**可查询的语义图**（存储于 SQLite/图数据库如 FalkorDB，部分实现支持 Cypher 查询），并通过 MCP（Model Context Protocol）server、IDE 插件（VS Code/JetBrains）等形式暴露给 LLM Agent 和开发者查询。

### 2.2 核心能力

| 能力维度 | 说明 |
|----------|------|
| 多语言静态解析 | 基于 Tree-sitter，支持 19～38 种语言（视实现而定），不依赖 LLM 理解代码语义 |
| 结构化图谱 | 函数/类/模块/导入/调用链/继承关系等实体与边，天然表达"谁调用了谁""谁实现了什么接口""改动影响范围" |
| 增量/自动同步 | 代码变更后自动增量更新图谱，而非全量重建 |
| 查询接口 | MCP 42 个工具 + 可选 Cypher 查询，支持自然语言问题映射到结构化图查询 |
| 本地化/隐私 | 全部处理与存储在本地，无需上云或调用外部 LLM API |
| CI 集成 | GitHub Action 形式在 PR 上自动生成"影响范围/测试缺口/建议评审人"等评论，`--graph-only` 模式跳过 embedding，索引速度提升 10～50 倍 |
| 降本增效 | 官方/社区数据显示：相比传统"grep + 多文件阅读"方式，Agent 工具调用次数减少约 70%，大型仓库场景运营成本降低约 35% |

### 2.3 优势总结

1. **确定性强、可解释、可追溯**：图谱的边（调用/依赖/继承）来自静态分析，而非 LLM 摘要，结果可复现、可解释，不存在"AI 编造关系"的幻觉风险。
2. **对"结构性问题"精准**：诸如"这个函数被谁调用""这个接口有哪些实现""改这个函数影响哪些下游"这类问题，图查询天然比让 LLM 阅读全文再推理更快、更准。
3. **规模扩展性好**：静态解析是工具链级别的确定性计算，复杂度与文件数/代码行数基本呈近线性关系（社区案例：Linux 内核级仓库可在数分钟内完成索引），不受 LLM 上下文窗口限制。
4. **增量更新成本低**：代码变更只需增量重新解析受影响的文件/符号，不需要像"重新生成一遍文档"那样全量重跑。
5. **降低 Agent Token 消耗**：Agent 可直接查询图谱定位相关代码片段，避免大范围 grep/遍历多个文件试探，显著减少工具调用轮次与上下文占用。

### 2.4 局限

- 图谱表达的是**代码的结构关系**（"是什么、调用了什么"），并不直接回答"为什么这么设计""这个模块的业务含义是什么"这类语义/意图层面的问题，仍需要结合注释、文档或额外的 LLM 摘要层。
- 需要为每种语言维护 Tree-sitter/LSP 解析器，对小众语言或高度动态特性的语言（如大量反射、宏生成代码）解析精度会打折扣。
- 需要额外的运行时组件（MCP server、可选图数据库），属于"新增基础设施"，而非纯文本方案。

## 3. GSD `mapping-codebase` skill 调研

### 3.1 是什么

GSD（Get Shit Done）是一套面向 AI 编码助手（Claude Code 等）的项目管理/工作流框架，其 `gsd-map-codebase` skill（`open-gsd/gsd-core` 仓库 `skills/gsd-map-codebase`）用于**"恢复"或"首次建立"对一个存量代码仓库的理解**，是 brownfield（存量项目）接入 GSD 工作流前的必经步骤。

### 3.2 工作机制

1. 编排器（orchestrator）检查 `.planning/codebase/` 是否已存在，决定是刷新还是新建。
2. **并行派生 4 个 `gsd-codebase-mapper` 子代理**，每个代理有独立的聚焦领域（focus area），使用 Read/Bash/Glob/Grep 工具阅读代码：
   - **tech**：产出 `STACK.md`（技术栈）、`INTEGRATIONS.md`（外部集成）
   - **arch**：产出 `ARCHITECTURE.md`（架构说明）、`STRUCTURE.md`（目录结构）
   - **quality**：产出 `CONVENTIONS.md`（编码规范）、`TESTING.md`（测试现状）
   - **concerns**：产出 `CONCERNS.md`（技术债/风险点）
3. 子代理**直接将文档写入磁盘**，编排器只接收"完成确认"而不接收文档正文内容，这是刻意设计——**为了让编排器自身的上下文占用最小化**。
4. 汇总校验 7 份文档是否都已生成（含行数校验），提交（commit）到仓库。
5. 提供 `--fast`（单代理轻量扫描，可指定 `--focus`）和 `--query`（基于已生成的 intel 做增量查询/diff/refresh）两种轻量模式。

### 3.3 核心能力总结

| 能力维度 | 说明 |
|----------|------|
| 产出物 | 7 份结构化 Markdown 文档，人类和 Agent 均可直接阅读 |
| 并行化 | 4 个子代理各自独立扫描一个维度，避免单代理承担全部上下文 |
| 上下文隔离 | 编排器不读取文档全文，只做完成度校验，控制主线程上下文膨胀 |
| 增量刷新 | 支持 `refresh`/`diff` 增量更新，也可 `--fast` 做轻量扫描 |
| 使用场景 | 适合"人类可读的架构/规范/风险总览"，作为后续 AI 规划（`/gsd-plan-phase`）的输入上下文 |
| 明确不适用场景 | SKILL 文档中明确注明：小于 5 个文件的琐碎代码库跳过该 skill |

## 4. CodeGraph 与 GSD `mapping-codebase` 的核心区别

| 维度 | CodeGraph | GSD `mapping-codebase` |
|------|-----------|--------------------------|
| **本质** | 静态代码分析工具，产出**结构化图谱**（图数据库/索引） | LLM 子代理编排流程，产出**自然语言摘要文档**（Markdown） |
| **构建方式** | Tree-sitter/LSP 语法解析，确定性算法 | 多个 LLM 子代理阅读代码后"总结/推断"，非确定性（不同次运行可能有细节差异） |
| **产出粒度** | 符号级（函数/类/调用边），可精确到"第 N 行调用了谁" | 章节级（架构描述、技术栈清单、规范总结），是人类可读的叙述性文字 |
| **回答的问题类型** | "谁调用了 X""改 X 影响哪些模块""有没有死代码" —— **结构性/关系性问题** | "这个项目是干什么的""用了什么技术栈""有哪些已知技术债" —— **概览性/语义性问题** |
| **可解释性/幻觉风险** | 低，边来自真实解析结果，可溯源到代码行 | 存在，LLM 摘要可能遗漏、误解或过度泛化，需要人工校对 |
| **更新成本** | 增量解析，代价随变更范围线性增长，可自动化触发 | 需要重新派生子代理阅读代码，`refresh`/`diff` 支持增量但本质仍是"重新总结"，成本高于纯语法解析 |
| **规模扩展性** | 强，工业级仓库（如 Linux 内核）可在分钟级完成索引，不受上下文窗口限制 | 中等，依赖并行度和 4 个子代理各自的上下文预算；SKILL 明确建议仅在有一定规模（≥5 文件）时使用，未针对"万级文件"场景做专门优化 |
| **基础设施要求** | 需要额外解析引擎/MCP server，部分实现需图数据库 | 无需额外基础设施，只需 LLM Agent 运行环境（Claude Code 等）与文件系统写权限 |
| **消费方式** | 需要通过 MCP 工具调用/图查询接口访问，适合"Agent 在编码任务中按需查询" | 直接是纯文本 Markdown，`git clone` 即可读，适合"Agent/人类快速获取项目全貌" |
| **适用阶段** | 贯穿开发全周期的常驻基础设施（IDE 内联提示、PR 影响分析、Agent 编码时的实时查询） | 项目接入 AI 工作流前的**一次性/周期性**"体检快照"，为后续规划提供背景 |

### 4.1 结论：两者是互补关系，而非替代关系

- **CodeGraph 解决"精确关系查询"问题**：当 Agent 需要回答"这个函数被谁调用""改这里会不会破坏别的模块"时，图查询比 LLM 阅读全文推理更快、更准、更省 token，且结果可复现。
- **GSD mapping-codebase 解决"项目全貌获取"问题**：当 Agent/新人第一次接触一个存量仓库、需要"这个项目是干什么的、用了什么技术、有哪些坑"这类叙述性总结时，结构化 Markdown 文档比图谱更直接易读，也更适合作为后续任务规划的输入上下文。
- 两者的产出物形态也决定了它们可以**组合使用**：先用 GSD 式子代理产出人类可读的架构总览文档，再用 CodeGraph 类工具作为常驻的"结构关系查询层"，供后续具体编码任务按需查询调用链/依赖细节，二者不冲突，且分别对应"知识管理组织方式调研"报告中提到的"仓库内置文档"（GSD 产出物适合归档于此）与"面向 Agent 的结构化索引/检索层"（CodeGraph 承担的角色）。

## 5. llm-wiki 类工具在万级文件规模下效果变差的原因分析

### 5.1 llm-wiki 类工具的典型工作方式

以 DeepWiki-Open（Grok-Wiki）、`lucasastorian/llmwiki`（Karpathy LLM Wiki 模式的开源实现）等为代表，其共同模式是：

1. 拉取/克隆整个仓库；
2. 对代码文件做 **chunk 切分**（按文件或按固定 token 长度）；
3. 逐 chunk 或逐文件调用 LLM 做**摘要/理解**；
4. 将多个摘要**再汇总**成更高层的页面（模块级 → 系统级），并生成**页面间的互链**（类似百科词条的"另请参阅"）；
5. 产出一组互相链接的 Markdown/HTML 页面作为最终 Wiki。

这与 CodeGraph（静态解析、确定性、增量）和 GSD mapping-codebase（有限的 4 个并行代理、聚焦维度明确、产出 7 份固定文档）有本质不同：**llm-wiki 的处理规模与"文件数量"直接强相关，且依赖多层 LLM 摘要的层层传递**。

### 5.2 效果变差的根因

1. **上下文窗口的硬约束被逐层放大**
   模型可处理的上下文有限（如 128K tokens 级别）。当文件数达到万级时，即使单文件摘要能控制长度，"汇总的汇总"这一层为了覆盖全局，仍需要把大量下层摘要拼接后再喂给模型做更高层归纳，极易逼近甚至超出上下文上限，迫使工具做截断/采样，导致遗漏。

2. **实例数（文件/chunk 数量）比总 token 量更容易造成性能塌陷**
   相关研究表明，随着"实例数"（这里可理解为参与同一轮推理的文件/chunk 片段数）增加，模型性能并非随 token 总量线性下降，而是在数量达到一定阈值后出现**更快的塌陷**——模型难以在大量并列片段中保持一致的关注度和交叉引用能力，容易出现"中间遗忘"（lost-in-the-middle）现象，其影响比单纯拉长上下文更显著。

3. **摘要层级越深，误差累积（drift）越严重**
   Wiki 生成通常是"文件摘要 → 模块摘要 → 系统摘要"的层级结构。每一层摘要都是对下一层的有损压缩，且由 LLM（非确定性）生成。文件数越多，需要的汇总层级越深，每多一层就多一次"理解误差/幻觉"的累积机会，最终导致顶层页面出现内容漂移、张冠李戴，甚至编造关系（尤其是在需要跨文件建立引用/依赖描述时，缺少静态分析兜底，纯靠 LLM 推断容易出错）。

4. **增量更新退化为近似全量重跑**
   万级文件规模下，代码持续变更是常态。llm-wiki 类工具若要保证"页面间互链关系"随代码演进保持一致，往往需要重新评估受影响的关联页面——但由于摘要之间是**软链接（LLM 生成的引用描述）而非结构化边**，很难像 CodeGraph 那样精确定位"这次改动只影响哪几条边"，最终倾向于大范围甚至全量重新摘要，导致更新成本随文件数近似线性甚至超线性增长，实时性和可用性同时下降。

5. **检索/生成的老化数据一致性问题**
   多数 llm-wiki 实现依赖"定时/触发式重新生成 + 向量索引"来支持问答，向量库和页面内容都存在**同步延迟**。文件数越多，一次完整刷新耗时越长，实际可用的 Wiki 内容与代码当前状态之间的时间差（staleness window）越大，用户越容易看到过期或前后矛盾的描述。

6. **成本与耗时呈非线性增长，倒逼降级处理**
   为控制成本和时延，工具在文件数过大时通常会自动降级策略（如采样部分文件、缩短摘要、降低模型能力档位），这是"主动放弃精度换取可用性"的工程妥协，也是用户能直观感知到的"效果变差"的直接原因。

### 5.3 与 CodeGraph / GSD mapping-codebase 的对照

| 失效模式 | llm-wiki 类工具 | CodeGraph（对照） | GSD mapping-codebase（对照） |
|----------|------------------|--------------------|-------------------------------|
| 是否受文件数量强约束 | 是，随文件数增加需要更多层摘要汇总 | 否，静态解析近线性扩展，不经过多层 LLM 归纳 | 部分，但通过 4 代理聚焦维度 + 明确产出 7 份固定文档，控制了归纳层级 |
| 是否有确定性结构兜底 | 否，页面间引用靠 LLM 生成的软链接 | 是，调用/依赖边来自语法解析，可复现 | 否，但只做一次性总览总结，不追求精确到符号级关系 |
| 增量更新代价 | 高，接近全量重跑 | 低，增量解析受影响部分 | 中，`refresh`/`diff` 支持增量，但仍需重新派生代理阅读 |
| 误差累积风险 | 高（多层摘要漂移） | 低（结构化边不经过多层压缩） | 中（单层摘要，无多级汇总，风险可控） |

**小结**：llm-wiki 类工具"效果随文件量变差"并非单一技术缺陷，而是其**"多层 LLM 摘要 + 软链接"这一架构选择的必然代价**——文件越多，需要压缩的层级越深，每层都会引入上下文截断风险和摘要误差，两者叠加导致规模超过万级文件时问题呈现出"非线性恶化"而非"线性变慢"的特征。这也解释了为什么 CodeGraph（用确定性静态解析替代深层 LLM 摘要）和 GSD mapping-codebase（用有限并行代理 + 固定产出结构控制归纳层级）在各自场景下都比"纯 LLM 摘要生成 Wiki"更能扛住大规模代码仓库。

## 6. 综合调研结论

### 6.1 三者定位总结

- **CodeGraph**：常驻的"结构关系查询基础设施"，解决"代码符号级/依赖级关系"问题，规模扩展性最好，适合作为 Agent 编码任务中的实时查询层，也适合接入 CI 做 PR 影响分析。
- **GSD mapping-codebase**：一次性/周期性的"项目全貌体检"流程，解决"新接触一个存量仓库时快速建立整体认知"的问题，产出物是人类可读的结构化文档，适合归档进代码仓库（延续此前"仓库内置文档"结论）作为 Agent 的入口上下文。
- **llm-wiki 类工具**：定位与 GSD mapping-codebase 类似（都是"生成可读文档"），但采用"多层 LLM 摘要 + 软链接"架构，在万级文件规模下会因上下文窗口约束、实例数塌陷、摘要误差累积、增量更新退化等多重因素叠加而明显失效，不适合作为超大型仓库的主力知识生成方案。

### 6.2 对"GitLab 知识库"既有方案的补充建议

结合此前两次调研（知识组织三种模式、GitLab CLI/API 精确寻址能力）的结论，本次调研进一步细化"代码强绑定知识"这一层的技术选型：

1. **超大型存量仓库（文件数达万级）**：优先引入 CodeGraph 类静态解析工具作为常驻结构查询层，避免依赖"LLM 遍历全仓库生成 Wiki"的方案；该层可与 GitLab 仓库共存，作为 Agent 查询代码结构关系的补充手段，而非替代 Git 仓库本身的文档存储。
2. **首次接入/存量项目体检**：可参考 GSD mapping-codebase 的"多代理聚焦维度 + 固定产出文档"模式，产出架构/技术栈/规范/风险等结构化 Markdown，归档进代码仓库（如 `ARCHITECTURE.md`/`STACK.md`），作为此前调研中"仓库内置文档"层的补充生成手段，降低人工撰写成本。
3. **不建议**在文件量已达万级规模的仓库上使用纯 llm-wiki 式"多层摘要生成 Wiki"方案作为主力知识库；如确需该类可视化/可浏览体验，应控制单次处理范围（按模块/子系统分治生成，而非整仓一次性生成），并优先依赖 CodeGraph 类结构化数据做锚点，减少纯 LLM 推断产生的漂移。

- [ ] 对比 GSD mapping-codebase 产出文档与团队现有 `ARCHITECTURE.md`/`AGENTS.md` 规范的字段对齐情况，评估是否可直接复用其 7 份文档结构
